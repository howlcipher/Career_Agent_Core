# ADR-004: Tracker Durable UID Checkpoint & Bounded Historical Catch-Up

## Status
Accepted

## Context
`pkg/tracker.StartTracker` originally had no durable position in the mailbox at all. Every scan re-derived its fetch window from `mbox.Messages`, the mailbox's current message count, fetching only the newest ~50 IMAP *sequence numbers* (`from = mbox.Messages - 50`). Sequence numbers are mailbox-relative and shift whenever mail is added or removed, so they cannot serve as a checkpoint even in principle, and anchoring to "the newest N" meant the window only ever moved forward with the mailbox: a message that fell outside it was never fetched again, by any future scan, under any circumstances.

Bug #534's production validation (2026-08-07) made this concrete: the tracker had been stopped for 14 days, and every message queued during that outage beyond the newest ~50 was permanently unreachable. `processed_emails` (message ID, primary key) already made re-acknowledging a message idempotent, but it is a *set*, not a cursor — it cannot tell a scan where to resume, only whether a given message has already been seen.

## Decision
1. **A durable checkpoint keyed by IMAP UID, not sequence number.** `storage.tracker_cursor` (`pkg/storage/manager.go`, singleton row `id = 1`) persists `uid_validity`, `forward_uid`, and a bounded catch-up range (`catchup_floor_uid`, `catchup_ceiling_uid`, `catchup_next_uid`, `catchup_complete`). UIDs are stable within one `UIDVALIDITY` generation (`github.com/emersion/go-imap`'s `client.UidFetch`/`UidSearch`), unlike sequence numbers.
2. **Two independent ranges, not one.** `forward_uid` is the high-water mark for ordinary new mail, advanced every scan. `catchup_next_uid` walks a separate, bounded historical window established once at bootstrap. Splitting them means a large historical backlog can never starve new mail: the forward range is always fetched and processed regardless of how much catch-up work remains.
3. **The historical floor comes from live evidence, not a hardcoded lookback.** At bootstrap (first-ever scan, or after a `UIDVALIDITY` change — see below), `storage.EarliestTrackableApplicationTime()` returns the earliest `discovered_at`/`applied_at` among `job_funnel` rows in an open, trackable status (`APPLIED`, `MANUAL_REQUIRED`, `AWAITING_REVIEW` — the same set `GetTrackedCompanies` and the tracker's own candidate-matching query use). An outcome email cannot meaningfully predate the earliest still-open application, so this date is a real evidence-based lower bound rather than "the last N days," and it naturally covers whatever the actual outage was instead of one specific incident's duration. `bootstrapTrackerCursor` (`pkg/tracker/imap.go`) then uses `c.UidSearch(&imap.SearchCriteria{Since: earliest})` to find the lowest matching UID and installs it as `catchup_floor_uid`. If no open application exists, catch-up is immediately marked complete — there is nothing left for it to recover.
4. **Both ranges are fetched in bounded batches per scan (`trackerRangeBatchSize`, currently 200 UIDs).** This bounds both the LLM call volume from any one scan and the amount of work a crash mid-scan can lose. Messages within a fetched batch are sorted ascending by UID and processed oldest-first.
5. **The checkpoint only advances past durably-handled work, and crosses fetched-but-empty stretches.** Each message's classification, matching, and persistence continue to commit atomically per bug #533's transaction shape; if a message's acknowledgement fails, `processMessages` stops and reports `complete = false`, and the checkpoint advances only to the last successfully handled UID (or not at all, if the first message failed) — a crash or transient failure mid-batch is retried from exactly that point on the next scan, not skipped. But IMAP UIDs are **not contiguous**: deleted mail leaves permanent gaps, so a fetched batch can legitimately contain zero messages while catch-up is nowhere near complete. The original version of this fix only advanced the checkpoint to the highest UID a real message carried, which stalled catch-up forever the first time it hit a gap wider than one batch — confirmed live 2026-08-08, a real ~200-UID gap froze progress indefinitely with no errors logged. The fix: when a batch is handled with `complete = true` (nothing failed, whether or not any messages were found), the checkpoint advances to the *end of the fetched range*, not merely to the last message's UID.
6. **A `UIDVALIDITY` change forces a full, safe re-bootstrap, never a silent skip.** RFC 3501's `UIDVALIDITY` is the explicit signal that a mailbox's prior UIDs no longer mean anything (e.g., the mailbox was recreated). `scanInbox` compares the stored `uid_validity` against the freshly `SELECT`ed mailbox's value on every scan; a mismatch (or no stored cursor at all — the pre-#534 or brand-new-database state) re-runs the same bootstrap procedure from scratch, adopting the new generation and re-deriving the catch-up floor from the same live evidence. This can re-fetch messages already durably processed under the old generation; `processed_emails`' Message-ID dedup (unrelated to this cursor) is what prevents that from duplicating any outcome write, not the UID cursor itself.
7. **`UNSEEN` search was considered and rejected** as a substitute mechanism: it depends on read/seen state the user (or any other mail client) can mutate independently of the tracker, which is not a property the tracker can rely on for correctness.

## Consequences
**Positive:**
- Downtime of any length — minutes, days, or weeks — no longer permanently loses outcome mail. The forward path covers ordinary steady-state traffic with the same cost as before; the catch-up path recovers the rest across as many future scans as it needs, without blocking new mail.
- A repository upgraded from the pre-#534 state initializes tracking automatically on its next scan (`GetTrackerCursor` returning no row is treated identically to a `UIDVALIDITY` mismatch), with no manual migration step.
- Regression coverage lives in `pkg/tracker/uid_cursor_test.go`, exercised against a real (in-process, not mocked) `github.com/emersion/go-imap/server` instance backed by a purpose-built test mailbox (`imap_server_test.go`) rather than a hand-rolled fake of the IMAP protocol.

**Negative:**
- A very large historical backlog (a very old evidence floor against a high-traffic mailbox) takes proportionally many scan cycles to fully drain, since each scan's catch-up batch is capped. This is deliberate — see decision 4 — but means "fully caught up" is not instantaneous after a long outage.
- The catch-up floor is derived once, at bootstrap, from whatever `job_funnel` evidence exists *at that moment*. An application that becomes newly relevant later (e.g., reopened) does not retroactively widen an already-established catch-up window; only a fresh bootstrap (a `UIDVALIDITY` change, or a new database) re-derives it.
- `EarliestTrackableApplicationTime`'s evidence set (`APPLIED`, `MANUAL_REQUIRED`, `AWAITING_REVIEW`) intentionally excludes already-resolved applications (`REJECTED`, `INTERVIEW_REQUESTED`, etc.); an outcome email for an application that resolved before the very first bootstrap ever ran is out of scope for catch-up, same as before this fix.
