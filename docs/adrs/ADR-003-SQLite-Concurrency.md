# ADR-003: SQLite Concurrency and WAL Mode

## Status
Accepted

## Context
The application utilizes SQLite (`applications.db`) for tracking execution states, managing job funnels, and caching learned ATS form mappings. With up to 10 concurrent worker goroutines reading and writing to the database simultaneously, the application consistently threw `database is locked` panics.

## Decision
1. Configured the SQLite connection string to use Write-Ahead Logging (WAL) journal mode, plus `synchronous(NORMAL)`, a `busy_timeout(5000)`, a `cache_size(-20000)`, and `temp_store(MEMORY)`: `?_pragma=journal_mode(WAL)&_pragma=synchronous(NORMAL)&_pragma=busy_timeout(5000)&_pragma=cache_size(-20000)&_pragma=temp_store(MEMORY)` (`storage.DSN`, `pkg/storage/dsn.go`). The `_pragma=name(value)` form is required by `modernc.org/sqlite`, the pure Go driver this project uses; it replaces the `?_journal_mode=WAL`-style query parameters the older `go-sqlite3` driver accepted.
2. Allowed a bounded connection pool rather than a single connection: `db.SetMaxOpenConns(10)` and `db.SetMaxIdleConns(5)` (`pkg/storage/manager.go`). `cmd/dashboard/main.go` opens its own independent connection to the same database file and likewise calls `db.SetMaxOpenConns(10)`. Lock contention between connections is absorbed by the `busy_timeout(5000)` pragma above: a connection that finds the database locked waits up to 5 seconds for the lock to clear instead of failing immediately.
3. Refactored the architecture to use a formal Repository Pattern (`pkg/storage`), ensuring raw SQL queries (`db.Exec`) are not scattered across concurrent worker files.
4. **Split the DSN by role (2026-07-31, bug/improvement #450).** `storage.DSN` (above) is now only for the connection that owns schema setup — `storage.InitDBWithPath`, used by `cmd/agent` and every other command except the dashboard. A second helper, `storage.ReaderDSN`, carries every pragma `DSN` does *except* `journal_mode`, and `cmd/dashboard` opens with it instead. Reason: `journal_mode` is a database-wide property change, and SQLite can refuse to make that change outright (`SQLITE_BUSY`) while another connection holds an open write transaction on a genuinely fresh, non-WAL database — `busy_timeout` does not cover that refusal, because it is not a lock wait, it is an outright "cannot change mode right now" error. A connection that never writes has no reason to ask for the change: once any writer has opened the database once, `journal_mode` is already WAL for every later connection, since it persists in the database file itself.
5. **Use a database trigger for the append-only funnel-stage ledger (2026-08-01, improvement #494).** Every `job_funnel.status` update writes a compact stage event in the same SQLite statement, recording the prior and next state, derived pipeline stage, normalized reason code, timestamp, and elapsed duration. This is more reliable than asking each Go call site to perform a second write: raw status writers cannot silently skip history. The event schema deliberately excludes job-page content and all applicant data; it is operational metadata only. The write cost is one indexed insert per actual state change, which is acceptable for this low-volume local agent and avoids reconstructing outcomes from raw logs.

## Consequences
**Positive:**
- WAL mode drastically improves read performance and allows concurrent reads while a write transaction is occurring.
- The `busy_timeout(5000)` pragma lets concurrent connections queue for a lock instead of failing with `database is locked`, so a bounded pool of up to 10 connections (`pkg/storage`) can share the same file without serializing through a single connection.
- The reader/writer DSN split (decision 4) removes the one scenario `busy_timeout` could never cover: a fresh database, opened for the first time by two connections at once, no longer risks the reader's connection being refused outright.

**Negative:**
- Concurrent writers can still queue for up to the 5 second `busy_timeout` under sustained contention; a write that cannot acquire the lock within that window still fails, though this has not been observed at this application's scale.
- Two independent connection pools now exist against the same file (`pkg/storage` and `cmd/dashboard`), each with its own `SetMaxOpenConns`. Nothing coordinates their combined connection count, so the total number of open connections to `applications.db` is the sum of both.
- The reader/writer split means `cmd/dashboard` alone, started against a database file that has never been opened by a writer, cannot bring the file into WAL mode itself — it has to wait for `cmd/agent` (or any other writer) to run at least once. This is a narrower version of the same fact already true before #450: the dashboard doesn't create the schema either way, so it shows no data in that state regardless.

## Superseded Decisions
- **2026-07-30:** Item 2 originally read "enforced a strict single-connection limit (`db.SetMaxOpenConns(1)`)." That is no longer what the code does. `pkg/storage/manager.go` sets `SetMaxOpenConns(10)` and `SetMaxIdleConns(5)`, and `cmd/dashboard/main.go` opens its own separate connection with `SetMaxOpenConns(10)`. Concurrency safety today comes from WAL mode plus the `busy_timeout(5000)` pragma absorbing lock contention, not from serializing all access through one connection. This section is left in place, rather than deleted, to record that the decision changed and why.
- **2026-07-31:** The "Known gap, not a decision" note that used to sit under Consequences described `cmd/dashboard` carrying the old `go-sqlite3`-spelled DSN literal and running with no busy timeout at all. That was bug #446, fixed well before this revision — `cmd/dashboard` has derived its DSN from `pkg/storage` ever since, and `TestDashboardDSNMatchesStorage`/`TestDashboardDSNCarriesABusyTimeout` in `cmd/dashboard/dsn_test.go` pin it so it cannot silently regress. The note is removed rather than left stale; decision 4 above documents the DSN's current, further-refined state.
